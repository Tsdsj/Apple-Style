# 审计：Apple-Style 能否指导 agent 做出一个可用的完整网站

审计日期：2026-10-19　·　审计对象：`main` @ `0fbdbe6`（四个技能 + Web 库，已含 Web 应用组件）　·　方法：文档走查 + 冷启动对比实测（数据见 [`evals/runs/2026-10-19-website/`](../../evals/runs/2026-10-19-website/README.md)）

> **结论**：能做出来，但“做得出”主要来自模型本身，不是技能。
>
> - **两组都做出了完整网站**：启用和未启用技能的两组 agent 都交付了可上线的 12 页官网，包括：
>   - 坏链为 0；
>   - 元数据与 404 齐全；
>   - 表单校验与成功反馈；
>   - 深浅色；
>   - 无 JS 时仍可浏览。
>
>   视觉质量相当。
> - **技能带来的可测差别在无障碍和验证纪律上**：
>   - axe 严重级违规：启用组 0 页和 1 页，未启用组 6–7 页（浅色下；文字对比度 50–59 个节点，正文链接只靠颜色区分）；
>   - 启用组测了 320px，未启用组有一个站在 320px 溢出；
>   - 启用组按 Review 格式记录证据。
> - **技能的代价**：库是为 App 写的，网站只用到约 20% 的样式，却要整包加载。
>   - 每页多传输约 160–190 KB（未压缩）；
>   - Lighthouse 移动端 LCP 慢约 0.7–1.3 秒；
>   - 性能分 86–97，未启用组为 99–100。
> - **网站特有的部分技能都没给**：全局导航、页脚、主视觉、价格表、FAQ、文章排版、上线清单、网站检查项。
>   - 启用组自写的 CSS（59–77 KB）和未启用组的整份样式（66–68 KB）一样多，库没有减少网站代码量。
>
> 要成为做网站的好向导，技能需要一条“内容网站”路径：网站构件、按需加载、网站检查清单。

---

## 1. 方法

1. **文档走查**：按 agent 实际会走的顺序读技能（`SKILL.md` → `rules-and-evidence.md` → `web-implementation.md` → 其他速查表 → `web/demo.html` → Review 技能），列出做完整网站需要的每一项，标注技能里有没有、说得清不清楚。
2. **冷启动对比**：让 4 个与本会话上下文隔离的子 agent 做同一个需求（虚构记账应用的中文官网，12 页，静态部署），A、D 启用技能，B、C 禁止读取仓库。
   - 交付后用同一套脚本检查：全站爬取；元数据与地标；六个宽度的溢出；浅色和深色下的 axe；键盘操作菜单；表单两种提交；静态托管下的深层 404；减弱动态效果与强制颜色。
   - 另跑 Lighthouse 移动端测三页。
   - 需求原文、逐项数据和复现命令见 [run README](../../evals/runs/2026-10-19-website/README.md)。
3. **偏差**：
   - 每组 2 个样本，只有一个任务，只能作探索性结论。
   - 评审者知道每个站点的组别，但评分以自动化检查为主。
   - 生成站点和评审用的是同一模型家族。
   - 4 个 agent 都因会话额度中断过一次后继续，因此不比较耗时和 token。

## 3. 技能确实起作用的地方

两个启用组的 README 和代码表明，技能在以下几处直接改变了决定：

- **四项独立判断**：两个启用组都判定为“跨平台网页 + 内容型营销网站”。因此：
  - 不用 `.as-window`、侧栏、检查器；
  - 不用 `data-density="desktop"`（A 写明“该档面向桌面 Web 应用，不适合营销页”）；
  - 没有把 iOS 浮动标签栏搬进网站。

  `SKILL.md` 把 `web/demo.html`（iPhone 界面）列为组件标记来源，本以为会把 agent 带偏，实测没有发生。
- **材质分层**：玻璃只用在浮动导航、唯一的主操作和窄屏菜单上，内容层全部是实色。没有出现玻璃叠玻璃。
- **颜色**：品牌青柠色白底只有 1.7:1。两个启用组都按技能的说法实测对比度，然后覆盖 `--as-accent`、`--as-action-bg`、`--as-accent-on-tint`，文字和按钮达到 5:1 以上。这就是启用组 axe 对比度违规为 0 的原因。
- **组件语义**：
  - 价格周期和外观切换用 `radiogroup` 分段控件；
  - 窄屏导航是“按钮 + 链接列表”的展开式导航，不是 `role="menu"`；
  - 表单使用 `.as-form*`，失焦和提交时校验，错误文字紧邻字段；
  - Toast 只作补充确认，不是唯一反馈。
- **许可**：不用 SF Symbols、不打包 SF 字体、不画 Apple 硬件和 App Store 徽章。
- **验证纪律**：按技能列出的宽度测了 320px，按 Review 的约定把 Safari、读屏软件和真机标为“未检查”。D 还据 WCAG 1.4.11 判断库默认的填充式输入框边界不足 3:1，并主动覆盖。

## 5. 文档走查：做网站时，agent 在技能里能找到什么

| 网站要素 | 技能中的指导 | 实测中 agent 怎么做 |
|---|---|---|
| 平台 / 应用类型判断 | **有**：四项判断，明确列出 content site、landing page | 两个启用组都判对，并写进 README |
| 页面结构、全局导航、窄屏菜单 | 只有“保留网页导航”“不要假窗口”，没有正面写法 | 用玻璃分组 + `.as-menu` 外观自拼，展开导航脚本自写 |
| 主视觉与大标题 | 无；字阶最高为 34px（iOS Large Title） | 各自用 `clamp()` 定义 48–80px 标题，中文断行各自处理 |
| 价格表、FAQ、文章、页脚 | 无 | 自写；FAQ 都用 `<details>` |
| 表单、空状态、Toast、分段控件 | **有**（本轮补的组件） | 启用组直接使用，表单行为一致 |
| 颜色、对比度、品牌色 | **有**：语义令牌、实测要求、各令牌的覆盖方式 | 启用组实测后覆盖，对比度违规为 0 |
| 字体与图标许可 | **有** | 都遵守 |
| SEO 元数据、OG、sitemap / robots、favicon、404 | 无 | 4 组全部自己做了，404 都用根路径以适配深层路径 |
| 性能 | 只有玻璃预算（约 20 个透镜） | 没人提到库本身的体积；启用组性能分更低 |
| 正文链接、装饰示意图 | 无 | 3 / 4 有链接问题；示意图处理各不相同 |
| 多页维护 | 无 | 全部复制，B 写了注入脚本 |
| 验证 | 宽度 320–2000、偏好设置、Review 证据格式 | 启用组覆盖 320px 并记录未检查项；未启用组有一组漏了 320px |

## 6. 建议（按投入产出排序）

> 已据此制定改造清单：[以网站为主场景](../plan/2026-10-19-website-first-plan.md)。

1. **内容网站速查表与构件**（W2、W4、W5、W8、W9）：
   - 页面骨架；
   - 页眉的两种写法；
   - 展开导航（含运行时）；
   - 页脚；
   - 展示字号；
   - 文章排版（链接默认下划线）；
   - 对比表和 FAQ；
   - 示意图的无障碍处理；
   - 多页维护选择；
   - 上线清单：元数据、OG、sitemap / robots、404 根路径、隐私与备案提示。
2. **按需加载**（W1）：样式拆出 App 外壳，提供压缩版；文档给出内容网站的最小加载方式，并让性能预算覆盖库自身的体积。
3. **Review 增加网站检查项和脚本**（W3、W6）：
   - 全站爬取；
   - 逐页元数据；
   - 深层 404；
   - 无 JS；
   - 320px；
   - axe 浅色和深色；
   - Lighthouse 预算；
   - 无头渲染限制的提示。
4. **输入框边界默认满足 3:1**（W7），修正安装后的失效引用（W10）。
5. **把本次需求加入 `evals/tasks.json`**（W11）。完成以上改动后重跑，每组至少 3 次，看启用组的自写 CSS 量和 LCP 是否下降、无障碍优势是否保持。

## 7. 局限

- **样本**：每组 2 个，只有一个需求，只有一个模型家族，结论只能作方向参考。
- **浏览器**：只用了 Chromium headless；Safari、Firefox、读屏软件和真机都未测。性能数据是 Lighthouse 的移动端模拟，来自未压缩的本地服务器，不是真实网络。
- **未覆盖的网站类型**：作品集、文档站、电商、多语言站点不在本次范围内。
